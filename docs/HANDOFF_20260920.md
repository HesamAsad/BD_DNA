## Gotchas that have already cost time today

1. **Monitors lie.** Three separate "ALL COMPLETE" signals fired while 14 jobs
   were running — two from stale job-name lists, one from my own impossible
   regex (`" ^(eps0|...)"`, a space then `^`). ALWAYS confirm with `bjobs`
   before believing a completion claim.
2. **Watchers orphan on restart -- key them on the job NAME, not the ID.**
   Anything keyed to a job ID dies silently when that job is resubmitted. This
   happened **four times on 2026-09-20**: `scalescore` twice, the b8 step-rate
   watcher, and the cache-ready launcher. `bjobs -J <name> -o stat` is the fix
   and `.scratch/launch_when_cache_ready.sh` now uses it.
3. **Pending is usually a missing `-U`.** `Not enough job slot(s) while advance
   reservation is active` means the hosts are fenced in reservations you did not
   request. See `docs/lsf_conventions.md` §9c. I re-made this exact mistake
   hours after writing that section.
4. **Not every host is an H200.** `lotfollahi-training-normal` (farm-gpu0201/2)
   is A100-80GB; `lotfollahi-training-parallel` (farm-gpu0307/8) is H100.
   Only `farm-gpu05xx` is H200. Pin `gmodel=NVIDIAH200` on training.
5. **farm-gpu0509 is `closed_Adm`** for firmware upgrades. Its 8 H200s look idle
   in `nvidia-smi` and `bhosts -gpu` but nothing can schedule there. Check
   `bhosts <host>` STATUS, not just GPU occupancy.
6. **Neither data phase checkpoints, and there are two of them.**
   `datasets.map` finalises only at the end, so killing at 57% loses it all --
   and after `Tokenizing` completes, `Grouping` runs the same 17.2 M rows again
   from zero. Budget ~7 h of data prep before a single training step, and
   pre-build the cache once in a separate job when several runs need it. Three
   jobs each did this work independently today.
7. **NEVER edit a shell script while a job is running it.** bash reads a script
   incrementally by byte offset, so an edit makes the running shell resume at a
   stale offset and execute garbage. `gb_mb256` (157588) did all 8 tasks, wrote
   its JSON, and then **exited 127** because `finetune.sh` was edited at 13:29
   while the job had been running since 03:26. Nothing depended on `done(157588)`
   so nothing stalled -- but it would have. Copy the script to
   `.scratch/<job>.sh` and submit that copy if you expect to edit the original.
8. **Silent no-op env hooks.** `--score2-window`, `--epsilon`, `CKPT_EVERY` and
   `WANDB_MODE=offline` all failed this way. After adding a hook, verify the
   flag reaches the process (`/proc/<pid>/environ` or `pgrep -af`).

## val/nll across rf settings is NOT comparable -- three reasons

Do not read `fd_human`'s val/nll against the 1.18386 of the checkpoint it
replaces. Three independent things differ.

1. **rf fires during validation.** `_bissm_use_right_flank` (`diffusion.py:1280`)
   is a plain `torch.rand() < p` with **no `self.training` guard**, so at rf=0.5
   about half of `fd_human`'s validation blocks get a clean right cache that an
   rf=0.0 run never receives. The measured worth of that cache on a trained
   model is +0.00807 nats/nt, so the bias is ~0.004 -- about the size of the
   whole apparent improvement (1.17870 vs 1.18386).
2. **Different numbers of validation sequences.** `trainer.limit_val_batches`
   counts BATCHES. The old run used `eval_batch_size=4`, the new one `8`, so at
   the same `limit_val_batches=64` they validate over different amounts of data.
   Device count moves this too.
3. **Different step counts**, which is the thing we actually want to measure and
   is confounded by 1 and 2.

MEASURED 2026-09-20 18:45 via `.scratch/ppl_eval_rf.sh`, all three on ONE GPU,
`eval_batch_size=8`, the full 128-batch validation set:

| job | checkpoint | rf at eval | val/nll |
|---|---|---|---|
| C 158518 | old `human-lr8192v2` `1-8000.ckpt` | 0.0 | **1.18508** |
| A 158519 | `fd_human` `2-10000.ckpt` | 0.0 | **1.18653** |
| B 158520 | the same weights as A | 0.5 | **1.18462** |

**The validation bias is A - B = +0.00191 nats/nt.** Real, in the predicted
direction, and about **half** the ~0.004 I estimated from the C-a right-cache
figure. So the bias accounts for roughly 40% of the apparent 0.005 improvement
in the training logs, not all of it; the remainder is the protocol difference
(`eval_batch_size` 4 vs 8 -> different amounts of validation data). Quote
**1.18508** for the old checkpoint, not the 1.18386 wandb figure, whenever
comparing against these.

**At matched protocol `fd_human` @10k is 0.00145 WORSE than the 8k checkpoint
it replaces.** This is expected and not yet informative: the old run's cosine
had `t_initial = 8000-800`, so at step 8000 it was **fully annealed**, while
`fd_human`'s is `t_initial = 60000-6000` and `lr_live` at step 12,139 is
**2.906e-4, still 97% of peak**. An un-annealed checkpoint always loses to an
annealed one. **The decisive comparison is at step 60,000**, and it must be run
at rf=0.0 with this same script.

Second possibility to keep in mind if the gap persists after annealing: training
at rf=0.5 may itself cost val/nll when evaluated at rf=0.0, because the model
spends capacity on a pathway the rf=0 evaluation never uses.

Use a FROZEN `<epoch>-<step>.ckpt`, never `best.ckpt` -- the training job
rewrites `best.ckpt` every time validation improves, and the first pair of these
jobs had to be killed for racing it.

## Codon-matched control: it flips the seq_unmask verdict (2026-09-20)

Compared on the **same 13,838 single-aa accessions**, joined on `accession`
(the codon-matched build rewrites `hgvs_nt`, so never join on that).

| arm | macro signed | macro abs |
|---|---|---|
| original, `block_marginal` | 0.0998 | 0.1314 |
| original, `seq_unmask` | 0.0853 | 0.1015 |
| **codon-matched, `block_marginal`** | **0.1383** | 0.1618 |
| **codon-matched, `seq_unmask`** | **0.1542** | 0.1666 |

Paired per-assay Wilcoxon over the 12 assays:

- codon matching helps `block_marginal` **+0.0385** (11/12 positive, p=0.0015)
- codon matching helps `seq_unmask` **+0.0689** (11/12 positive, p=0.0015)
- **interaction +0.0303 (10/12, p=0.0122)** — it helps `seq_unmask` nearly 2x as
  much

READ: the earlier "`seq_unmask` is a decisive negative" conclusion was an
artifact of the codon confound. Against a random-codon reference the within-block
sequential conditioning spends itself predicting synonymous codon choice; against
a codon-matched reference the same conditioning becomes the **best BD estimator
we have** (0.1542). `seq_unmask` is only worse on the original data
(-0.0145, 5/12, p=0.34 — itself not significant).

Caveat: 0.1542 is on 13,838 rows, the 0.1433 eps=0.95 headline is on 21,250.
Not directly comparable; on the matched rows the eps=0.9 arm (`cm-b8-eps09`,
158249) is the missing third point.

| BiSSM-BD b8 `seq_unmask` (gp, L=512) | 0.0921 | **0.1687** | +0.0765 | 12/12, p=0.0005 |

**AR mean gain +0.0637, BD mean gain +0.0558, difference +0.0080, 6/12
positive, p=0.62 -- not differential.**

Codon matching is a large, *universal* win: every arm gains 0.04-0.08 and no arm
has fewer than 10 of 12 assays moving the right way. It is a defect in the
benchmark, not an explanation of the objective gap. Within the matched-geometry
column the AR/BD ratio goes **2.24x -> 1.59x**, and that narrowing is
`seq_unmask` becoming usable, not AR losing ground.

Cross the codon confound off the list of candidate explanations, alongside
sharpness ([[ar-bd-gap-is-not-sharpness]]) and the MC-sample count. What is left
is measured in the next section.

How to read the grid: the codon-matching effect is WITHIN an arm, so geometry is
held and it is clean. The AR-vs-BD contrast is only legible WITHIN a geometry
column -- the AR arms run `--genomic-prefix` at L=512, and a BD arm without the
prefix at L=256 is not comparable to them.

GOTCHA: `--genomic-prefix` spends 256 of the length budget. The first submission
(158393-158398) passed `MODEL_LENGTH=256` for the BD arms and all four died with
`Sequence of length 207 exceeds model length 0`. With a prefix, L = 256 + seq.

## The AR-to-BD gap is a DENSITY gap (2026-09-20 18:00) -- pre-register this

`scripts/eval/dnahnet/density_vs_discrimination.py`. At **fully matched
geometry** -- both arms with `--genomic-prefix` at L=512, the same 13,838
codon-matched rows, and the same autoregressive factorisation, because
`seq_unmask` at block b IS the chain rule
`sum_b sum_j log q(x_{b,j} | x_{<b}, x_{b,<j})`:

```
DENSITY  wild-type NLL per nucleotide     AR 1.1193   BD 1.2907   gap +0.1714 nats/nt
         fraction of the ln4 budget       AR  19.3%   BD   6.9%
         relative density shortfall of BD           64.2%

RANKING  macro signed Spearman            AR 0.2674   BD 0.1687   ratio 1.59x
         relative ranking shortfall of BD           36.9%
```

**The density shortfall (64.2%) is LARGER than the ranking shortfall (36.9%).**
BD is not a well-calibrated density model that ranks badly -- it is a
substantially worse density model whose ranking is, if anything, better than its
likelihood deserves. So the lever is the model, not the scoring functional, and
the four full-data runs are the right experiment rather than another estimator.

**Pre-registered endpoint, decide this BEFORE `fd_b8` lands:** if more training
is the answer, the wild-type NLL gap must close along with the MaveDB gap. Score
`fd_b8/checkpoints/best.ckpt` with `cmgp-b8-sequnmask`'s exact settings and read
both numbers. Closing MaveDB *without* closing the 0.1714 nats/nt density gap
would falsify this reading and mean something else is going on.

Comparability rules the script enforces, and refuses to run without: the BD arm
must be `seq_unmask` (a NELBO is a bound, so comparing it to an exact NLL
measures the bound's slack), the AR arm must be an exact-NLL `block_size=1` arm,
and `genomic_prefix` must match on both sides.

Side note: the genomic prefix is worth **+0.0145** to `seq_unmask` on
codon-matched data (0.1542 -> **0.1687**, the best BD number anywhere), while on
`block_marginal` its apparent gain was pure confound. The prefix helps the
estimator that can actually use left context.

## The BD estimator ladder REVERSES on codon-matched data

All four on the same 13,838 rows. Confound-free, so signed == partial and no
stripping is needed (`nt-base` is -0.017, `pro-base` undefined):

| estimator | codon-matched | original | forward passes |
|---|---|---|---|
| `block_marginal` | 0.1383 | 0.1422 | **1** |
| NELBO eps=0.9, MC-128 | 0.1429 | 0.1438 | 128 |
| `seq_unmask` | 0.1542 | 0.1369 | 8 |
| **`seq_unmask` + genomic prefix** | **0.1687** | 0.0921 | 8 |

On the original data the ordering is `block_marginal` ~= eps0.9 > `seq_unmask`.
On codon-matched data it **inverts completely**: `seq_unmask` + prefix beats the
128-draw NELBO by +0.026 at 1/16 the cost, and `block_marginal` drops to last.

Two consequences for how to score the new checkpoints:

1. **Score `fd_b8` with `seq_unmask --genomic-prefix` as the headline**, not
   with NELBO and not with `block_marginal`. The old default was chosen on a
   benchmark whose references have since been rebuilt.
2. **The "one pass matches 128 draws" shortcut is weaker here.** On original
   data `block_marginal` tracked eps=0.9 to 0.0016; on codon-matched data the
   gap is 0.0046. Still cheap and still close, but do not quote it as exact.
   The `scalescore` watcher uses `block_marginal` deliberately -- it is measuring
   a *trend* against tokens seen, where cost per point matters more than the
   last 0.005.

## The protein-event baseline is undefined on single substitutions

`n_pro_events` over the full set takes three values: 66 rows at 0 (WT), 15,739
at 1, 5,445 at 2. Over the 13,838 codon-matched rows it takes **one** value: 1.
So the 0.3093 "0 params beats every model" baseline has zero variance there and
predicts nothing. It is a wild-type / single / double detector, and on the
single-substitution subset that a variant-effect predictor is actually asked to
rank it does not compete. Say this whenever the 0.3093 number is quoted.

`partial_corr.py` prints `nan` in its `pro-base` column for codon-matched files
for exactly this reason -- that nan is correct, not a bug.

## Three more silently-unforwarded flags (fixed 2026-09-20)

`--right-flank` was accepted by `score_mavedb.py` and **never emitted by
`mavedb_score.sh`** -- so the user's instruction "turn right flank on in all eval
branches" could not have taken effect. Same class as `--epsilon`. An audit of
every wrapper/entrypoint pair found two more that matter:

| wrapper | flag | consequence |
|---|---|---|
| `mavedb_score.sh` | `--right-flank` | rf could never be set at scoring time |
| `deg_score.sh` | `--epsilon` | the DEG noise band has never been swept |
| `genomic_benchmarks.sh` | `--seed` | no probe number carries a seed error bar |

All three forwarded now, and `tests/test_wrapper_flag_reachability.py` is the
ratchet (6 tests, passing) with an ALLOWED list that must name a reason.

**Patch shell scripts by atomic rename, never in place** (`write .new; bash -n;
mv`). A running job holds the old inode open and is unaffected. This is what
gotcha 7 costs you if you forget.

## Two traps in reading these numbers

**The genomic prefix does NOT help BD, despite looking like it does.**
`gp-b8-blockmarg` (158402) scores signed **0.1486** on the full 21,250, above
every other BD arm -- but its partial is 0.1252, identical to the arms it
"beats", and its full partial (also stripping protein events) is **0.1085, the
worst of the three**. The whole apparent gain is confound. Do not quote 0.1486
as a BD best. Always read `partial_corr.py`, never the signed column alone.

**On codon-matched data signed == partial, and that is the point.** Both
confounds vanish by construction there (`nt-base` collapses -0.1786 -> -0.0170,
`pro-base` becomes undefined), so those numbers need no stripping -- which also
makes them the honest ones to compare across objectives.
