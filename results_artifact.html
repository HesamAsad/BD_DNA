BD3-LM DNA: all results

This page compares six DNA language models. All six were trained on the same prokaryote data, for the same 8000 steps, on four H200 GPUs. Each has about 100 million parameters. We report the raw weights at step 8000, with no EMA averaging. Each model used its own tuned optimizer settings.

The models differ in two ways. The first is how they were trained. AR means autoregressive: the model predicts one nucleotide at a time, using only the nucleotides to its left. BD means block diffusion: the model hides a random subset of the nucleotides and learns to fill them back in.

The second is the backbone. uSSM is a Mamba-2 state space model that reads left to right. BiSSM is the same model with a second scan that also reads right to left. Transformer is a standard attention model.

Two measurements appear throughout. Val NLL is the negative log-likelihood on held-out DNA, in nats per nucleotide. Lower is better. Guessing uniformly among A, C, G and T gives 1.38629, so that is the worst useful score. MaveDB is a set of 21,250 measured E. coli K-12 variants across 12 experiments. For each variant we score the wild-type sequence and the mutant sequence, then check whether the difference between those two scores lines up with the measured effect. We measure that with Spearman rank correlation.

Why the block diffusion models score lower on MaveDB

The autoregressive models score about three times higher than the block diffusion models on MaveDB. This is the largest difference we measured anywhere.

We suspected the difference came from how we measure the block diffusion models, not from the models themselves. There are four ways that could happen. We tested all four. None of them explains the difference.

What is left is how the models were trained. Compare uSSM-AR with uSSM-BD. Same backbone, same data, same number of parameters. We can even score them the same way, because uSSM-BD reads left to right, so its exact likelihood can be computed. The only thing that differs is the training objective. uSSM-AR scores +0.21644. uSSM-BD scores +0.06689.

The val NLL column says the same thing on its own: 1.19305 against 1.28691. The block diffusion models predict DNA less sharply. A less sharp model gives the wild-type and the mutant almost the same score. The difference we need to detect is about 0.01 nats, and it gets buried.

Why does block diffusion produce a less sharp model? Because it has to learn a much bigger job. The autoregressive model learns one thing: predict the next nucleotide from everything on the left. The block diffusion model has to handle every possible pattern of hidden positions, at every hiding rate from 5 percent to 90 percent. With the same number of parameters, it spreads its capacity across all of those cases.

How much score is left after removing the easy shortcuts

A model can score well on MaveDB without understanding DNA at all. Variants with more mutations tend to be less fit. So simply counting mutations already produces a score.

Partial correlation removes that shortcut. We rank every value, subtract off what three counting features predict, and then correlate what is left over. The three features are: how many nucleotides changed, how much the length changed, and how many separate edit events there were. The script is scripts/eval/dnahnet/partial_corr.py.

One thing block diffusion can do that autoregressive models cannot

An autoregressive model reads left to right. It can never look at the DNA to the right of the position it is predicting. A block diffusion model can. We tested whether it actually uses that ability.

We trained one BiSSM model with the right-side cache switched on half the time. We call this the C-a model. Then we picked a block in the middle of a sequence and scored it twice: once with only the left side available, and once with the right side available too.

Both scorings use the same weights, the same noise level, and the same hidden positions. The block being scored is never inside either cache, so neither run can see the answer. The only difference is whether the right side is supplied.

BiSSM trained with NELBO, no right cache NELBO, clean right cache Δ nats/nt Reading
C-a · rfp=0.5111898 1.24181 1.23373 +0.00807 Clean right context helps.
de-novo · rfp=0.0103297 · negative control 1.24146 1.27074 −0.02928 Never trained on a right cache, so it is hurt by one.

The second row is the control, and it is what makes this result trustworthy. That model was never trained with a right-side cache. When we hand it one, it gets worse. That is exactly what should happen. If the cache were secretly leaking the answer, this model would have improved too. It did not.

The C-a model gains 0.00807 nats per nucleotide. To put that in scale: the entire difference between Transformer-BD and BiSSM-BD is 0.00096 nats, so this effect is about 8 times larger. We scored 15,728,640 nucleotides in each row. No autoregressive model can do this at all.

The ability is not free. Training with the right-side cache half the time costs 7916 PFLOP against 6571 PFLOP for plain BiSSM-BD. That is 1.20 times the compute, and it makes C-a the second most expensive model here.

Is 0.008 the ceiling? No — the model is losing most of it

0.00807 nats per nucleotide is a small number, so we asked whether it is small because DNA has little right-context information, or because the model fails to carry the information that is there. Those two explanations predict the same headline figure, so we separated them with one scoring run on the existing model, no retraining.

Two measurements from the same run. First, fix attention on the single position closest to the cache and vary how much clean suffix the cache is built from. At one step away the model's own signal decay barely matters, so this measures what the data offers. Second, use the whole suffix and watch how the gain falls off with distance from the block edge. That measures what the model delivers.

The data is not the limit. The left column is still climbing steeply at 128 nucleotides and only flattens past 1024. Prokaryote DNA carries useful right-context information out to roughly a kilobase. An earlier estimate suggested the value might saturate by about 26 nucleotides, which would have meant 0.008 was already the ceiling for a perfect model. That estimate is now ruled out.

The model is the limit. The right column shows half the available gain is lost one nucleotide into the block, and 98 percent is lost by the far side. The data supports 0.08458 at the edge; averaged over the block the model delivers 0.00807. If the signal did not decay, the block average would be 10.5 times larger. The nearest 64 of 256 positions carry 51 percent of the whole effect.

A control we should have run earlier. We rebuilt the cache from a different sequence's suffix. The correct suffix helps by 0.00807; a mismatched one hurts by 0.03127, which is worse than having no cache at all. So the gain is not a generic benefit of feeding the model any non-zero state. It reads what the cache actually contains.

This points at the recurrent decay rather than at training or data. The measured per-head signal half-life in this model is 4.66 nucleotides, and no head exceeds 256. Two things bound how far suffix information can travel: how fast the state decays, set by the A_log and dt_bias parameters, and how much it can hold, set by the state size, currently 64. Both need retraining to change, and both now have a measured target rather than a guess.

Training compute, and why the number we logged was wrong

During every run we logged a compute figure to wandb, called trainer/total_pflop. That figure is wrong. It was computed from only six things: parameter count, sequence length, number of layers, hidden size, block size, and whether cross attention is on.

Two mistakes follow from that. First, it charges an attention cost to every model, including the state space models, which contain no attention at all. Second, it never counts the extra passes that block diffusion runs on a state space backbone. We recomputed the real numbers by reading what the code actually does in the forward pass. The script is scripts/eval/training_flops.py.

These numbers are correct, and we checked them against the hardware. We ran a counter that records the arithmetic the GPU is actually asked to perform, at seven sequence lengths from 2,048 to 131,072. For the Transformer the derivation is exact: the counter cannot see fast attention, and its shortfall matches this table's attention term to the decimal at every length.

The two Transformer rows were revised upward on 2026-08-24. We had charged every backward pass at twice its forward cost, which is exact for matrix multiplication and wrong for attention: differentiating attention needs five score-shaped products against two going forward, so it costs two and a half times its forward pass, not two. Transformer-AR moved from 4567 to 4910 and Transformer-BD from 8194 to 8847. The state space rows contain no attention and did not move.

For the state space models the counter read 1.35 to 1.37 times higher than this table. We first read that as our derivation missing work, and an earlier version of this page said so and inflated these rows by 37 percent. That was wrong. The next section explains what the discrepancy really was; the figures above stand as written.

Why the linear model is not the fast one, and where that changes

A state space model does less arithmetic than a Transformer, because it never compares every pair of nucleotides. Whether it is actually faster is a separate question, and the answer depends on the sequence length.

Everything in this section was remeasured after four implementation fixes (a fused gated RMS norm, a padded causal convolution, a shared-projection bidirectional pass, and folding the norm weight into the fused kernel on both architectures). Earlier versions of this page reported a crossover of 18,600 and then 13,137 nucleotides; both came from slower code. Every fix was verified numerically identical in double precision, so no trained model's likelihood changed — only what the backward pass keeps in memory.

What the three scalings actually measure

The missing 27 percent was never real work. It was a bug in the measuring tool. PyTorch's FLOP counter takes a groups argument and ignores it — its own source says it skips that detail "for the sake of brevity". Our convolution is depthwise: each of the 1,664 channels is filtered independently. The counter bills it as if every channel were mixed with every other, which is 1,664 times more multiplication than happens. It went unnoticed because our code calls the convolution as a plain function rather than as a layer, so the counter files that work under no layer at all.

Removing the phantom makes the two accounts agree exactly. For uSSM-AR at 8,192 nucleotides, per sequence, forward and backward, in TFLOPs: derived 5.180 + phantom convolution 2.177 − the scan the counter cannot see 0.237 = 7.120, and the counter reported 7.120. The residual is zero to three decimals.

So the derivation was right the whole time and the counter was wrong. For uSSM-AR this is now exact rather than approximate: modelling the run as linear layers plus the head plus the mis-scored convolution, and charging the scan zero, reproduces the counter's total to the digit at all five measured lengths — 3,561,989,090,304 at 2,048 rising to 56,962,011,638,784 at 32,768, with a remainder of exactly zero each time.

BiSSM now closes too, once it is compared against the right thing. We first measured it about 20 percent adrift, then found the cause: we were charging the bidirectional pass two complete passes, which is what the trained runs paid, while the code being measured now shares its input and output projections between the two scan directions. Charging only the doubled parts brings the gap to 1.9 percent, and flat across 2,048, 8,192 and 16,384 nucleotides.

What is still open. That last 1.9 percent is unexplained, and so is the scan term, which is 4.6 percent of the total and runs in a kernel no counter can enter. The two are the same size, so the honest reading is that we have closed this to about the precision of the one term nobody can measure, and no further.

One correction to the paragraph above. We wrote that the convolution is billed to no layer at all. That is wrong: measured directly, the work belonging to no layer is 0.05 percent, not 27. The part that matters is still true — the convolution has no entry of its own, because the code calls it as a plain function rather than as a layer — but the arithmetic is charged to some ancestor rather than left unowned. The tool's layer-by-layer figures turned out to be unusable for a separate reason: a dropout layer, which performs no multiplication whatsoever, is credited with 63 percent of the model's arithmetic. None of this affects the totals, which never depended on which layer the work was filed under.

Training both models at 32,768, where the state space model is the cheaper one

The measurements above are microbenchmarks. We then trained both models for real, at length 32,768, to answer two questions. Does the speed advantage survive four-GPU distributed training? And does the extra context make the state space model a better model, not just a faster one?

The setup is as controlled as we could make it. We rebuilt the training data from the same source shard with the same row cap as the 8,192 runs, changing only how it is cut into sequences, so both length settings see identical nucleotides. Global batch stays at 64, so each model keeps the learning rate it was tuned with. 2,000 steps at length 32,768 is 4.1943e9 nucleotides, matching the 8,192 budget to four decimal places. Both models ran on four H200s with exclusive access.

The speed prediction was right to within one percent. A single-GPU microbenchmark said BiSSM would be 1.39 times faster at this length; real four-GPU distributed training gave 1.38 times, finishing nearly two hours earlier. A number from a short benchmark holding on a seven-hour distributed job is what makes the crossover credible rather than an artefact of measurement.

Both figures are from the code as it stood at the time. The implementation has since got faster on both sides, and at this length the microbenchmark now reads 1.80 times. The 1.38 measured in training remains the honest number for that run; it is not a prediction of what a rerun would give today.

The quality prediction was wrong. Longer context did not make the state space model better. It came out 0.00492 nats behind, and the gap grew rather than shrank: at length 8,192 it was 0.00096 nats, so moving to 32,768 made it about five times worse. BiSSM also stopped improving at step 1750 while the Transformer was still improving at 1950.

During the run we reported an apparent BiSSM lead of about 0.007 nats. That was a mistake in reading the logs: the checkpoint messages carry step numbers that we misaligned, and the corrected trajectory shows BiSSM converging faster only over the first 200 steps, then matching, then slowly falling behind. The final number is the one that counts.

So the two claims separate. Past about 14,200 nucleotides the state space model trains faster, and it costs 0.005 nats of likelihood to do so. That is a speed argument with a measured price attached, not an argument that recurrence models DNA better. On this data it does not.

One caveat on the numbers themselves. These runs took 2,000 optimizer steps, not 8,000, because we matched the nucleotide budget while holding global batch at 64. Both models took that hit equally, so comparing them to each other is sound, but neither value should be compared with the 8,192 rows in the first table, which had four times as many steps.

What it actually costs to generate DNA

Neither compute figure above measures generation. The forward-pass benchmark times a single forward — for a block-diffusion arm that is one noise-and-denoise step, when generation needs T of them. The cache benchmark is real generation but reports memory only, for two arms. So we swept it properly: 69 runs, three block-diffusion arms × three output lengths × seven values of T, plus both autoregressive arms once per length.

The result inverts what the benchmark was written to expect. Block diffusion is not the expensive one at any T we reached. The count that sets wall-clock is forward passes, not token-updates: autoregressive decoding does L of them, block diffusion does (L/b) × T. With a block size of 256, block diffusion does fewer forward passes whenever T < 256 — and the sweep stops at 64. The true break-even sits at T = b = 256, outside this grid.

Memory is the cleaner architectural story. The state-space arms are flat in output length — 0.72–0.73 GB with a 4.7 MiB cache whether generating 1,024 or 16,384 nucleotides. Transformer-BD grows 1.19 → 1.37 GB and carries a 468 MiB cache, a hundred times the state. That is the linear-versus-quadratic claim showing up in a real generation loop rather than a forward-pass proxy.

Transformer-AR is flat at about 125 tokens/s at every length — a sliding KV cache gives constant per-token cost. uSSM-AR is roughly half that, rising 45 → 64 tokens/s with length as its fixed per-step overhead amortises: the launch-bound signature, not a bandwidth limit. The recurrent decode does not beat a KV cache at these lengths.

There is no quality axis here. Low T is cheap and worse, and nothing in this sweep measures how much worse. This is a cost curve, not a cost/quality curve. Pairing sample likelihood or motif recovery against T is what would close that, and it has not been run.

One measurement caveat: T = 1 runs first in each group and absorbs warm-up, so several T = 1 points read slower than their T = 2 neighbours. The T ≥ 2 curve is the trustworthy one.

Two collection bugs had to be fixed before these numbers existed, and both exited with a success code while losing data: the two harnesses each write to a fixed summary.json, so a shared output directory meant 68 of 69 runs overwrote one file; and they nest their results under different keys, so every Transformer-AR run was silently dropped and the fastest autoregressive arm was simply absent from the first table.

Measured against Caduceus, on Caduceus's own benchmark

Caduceus (Schiff et al. 2024, arXiv:2403.03234) is the closest published relative of our model: a bidirectional Mamba for DNA, with shared forward and reverse weights exactly as ours has. It adds reverse-complement equivariance, meaning it treats a DNA strand and its complement as the same object by construction.

Correction. An earlier version of this page said Caduceus is “trained on the human genome at 131,072 nucleotides of context, against our 8,192”, and used that to excuse a gap. That is backwards. Their 131k model is used for variant-effect prediction. The model in the GenomicBenchmarks table is caduceus-ph_seqlen-1k_d_model-118_n_layer-4: 4 layers, 471 thousand parameters, 1,024 nucleotides of context. Ours is 100.7 million parameters at 8,192. We were losing to a model 214 times smaller and explaining it away with an advantage they do not have.

It is also trained differently. Caduceus uses masked language modelling, which produces representations for classification. We use block diffusion, which produces a generative model. The question is whether our objective gives up representation quality to buy that.

We ran the 8 GenomicBenchmarks classification tasks two ways on two of our checkpoints. The probe freezes the model and fits a logistic regression on its output. The fine-tune trains the whole model, which is what Caduceus does and therefore the only like-for-like comparison. One checkpoint was pretrained on prokaryote DNA, the other on human DNA, everything else identical.

Reading the SSM's own latent instead of pooling tokens: it does not work

Everything above reads the model by mean-pooling its per-position hidden states. For a block diffusion model that is a choice, not a given — and arguably the wrong one. A Mamba-2 model carries a fixed-size recurrent state, the thing a scan would need to continue exactly, and that state is the architecture's own whole-sequence summary. Running it forwards and backwards over a sequence gives a symmetric summary with no pooling at all. It is also the closest thing this architecture has to a classification token, since the model has none.

We built it and ran the full 2×2 — both readouts on both checkpoints, all eight tasks, frozen features with a linear probe.

The latent loses, on 6 of 8 tasks and on both checkpoints. The honest statement is “clearly not better” rather than “significantly worse” — eight tasks cannot resolve a 0.005 difference, and the sign test gives p = 0.29. What is unambiguous is the absence of any win large enough to build on.

Its one big win is a measurement artifact, and checking that was the point of the exercise. The latent beats pooling by +0.064 on human_ensembl_regulatory — by far the largest effect in the table. That task turns out to be 91.3% solvable from sequence length alone (a depth-8 decision tree; its three classes have cleanly separated length bands with medians 600, 400 and 315). The recurrent state is length-aware by construction, because it has integrated exactly as many steps as the sequence is long. Mean pooling is length-blind by construction, because it divides by the count. So the win is the latent carrying one scalar for free, not representing DNA better — and both readouts sit far below the 0.913 that length alone achieves.

A linear model on raw length scores only 0.475 here, which is exactly why this is easy to mistake for a real gain. Strip that one task out and the latent's deficit widens to −0.015, winning 1 of 7. The other win, human_enhancers_ensembl, is the task whose test set is 37.8% duplicated from train, so it rewards memorisation rather than representation.

What this says about the architecture. The fixed-size state does not concentrate more task-relevant signal than the distributed per-position states — it concentrates slightly less. That is the compression limit showing up on third-party benchmarks rather than on our own synthetic ladder: a good smooth summary, a poor exact one, which is the same conclusion the copy-gate ceiling and the 1–2 kb effective range reached by other routes.

Scope, so this is not over-read: frozen probe only, not the fine-tune path, and only the last-layer head-averaged variant (3072 dims). The all-layers and raw-state variants were not run on the suite — at 196,608 dims the smallest task has 968 training rows, so we do not expect them to rescue it.

The timescale experiment, and the measurement that undid it

A selective state-space model forgets at a rate set per head: the influence of a nucleotide d positions back decays as 2−d/τ, with τ = ln2 / (A · dt). Reading τ off the trained weights said our models had collapsed to a one-to-two nucleotide memory — no head above 100 nucleotides — which would make every long-range claim on this page moot. So we built a depth-scheduled initialisation giving deep layers geometrically longer τ, and trained two arms from it: one letting dt learn freely, one freezing it so the schedule could not be undone.

The collapse was a measurement artefact, and the freeze does not freeze anything. τ had been computed from dt_bias alone. But dt is input-dependent — dt = softplus(dt_proj(u) + dt_bias) — and freeze_dt pins only the bias, leaving the projection free to compensate. Measured on real validation data, it does exactly that: the frozen arm's projection pushes dt 26.9× up, the learned arm's pulls it 12× down, and both land in the same place.

A genuine positive falls out anyway: both arms grow a depth-increasing runtime profile unforced, from about 3 nt at layer 0 to 1.5 kb at layer 11. The schedule steepens a profile the model already learns on its own.

A problem with the MaveDB benchmark itself

The MaveDB DNA sequences are not real genome sequences. They were redesigned to code for the same protein using different codons.

We searched the E. coli K-12 reference genome (NC_000913) for all 12 target sequences. None of them are in it, on either strand. The proteins do match the real genes exactly, at a known amino acid offset. But the DNA matches only 75 to 87 percent: FecA 75.0, yaiA 78.8, argR 79.7, sucB 83.3, exbD 83.3, nusA 83.6, cspA 86.3, CspA 86.9. Four more experiments do not match at the protein level either.

This matters because a DNA language model mostly learns codon usage and short local patterns. Every model on this page is being asked to score DNA that no organism contains, written with codon usage 13 to 25 percent away from what it was trained on. The same is true of dnaHNet's 0.3266, and of every other published score on this benchmark.

This does not explain why our autoregressive models beat our block diffusion models, because that comparison is between our own models on the same data. But it probably limits how well any DNA model can do here. It is worth saying in the paper, next to the zero-parameter baseline of 0.30931.

The 256-nucleotide prefixes we used in the cache test are real genome sequence. We checked them separately: all 12 experiments have one, each is exactly 256 nucleotides, every letter is A, C, G or T, and GC content runs from 0.375 to 0.559 with a mean of 0.475, close to the E. coli genome value of 0.508. There are 7 different prefixes because the 12 experiments cover only 7 genes. So the cache test gave each model genuine upstream DNA, and the models still did not benefit. Note what that test asks of a model though: read a real promoter, then a gene body written in scrambled codons. That mismatch may be why the extra context does not help, and no amount of training would fix it.

Engineering results

  • We made the state space models about 4 to 5 times faster to train. The original code computed block boundaries one block at a time, which meant 372 tiny scan calls per micro-batch. We rewrote it to work one layer at a time, which needs only 24 calls. BiSSM got 3.96 times faster and uSSM-BD 4.94 times faster. The loss and the gradients are unchanged. We checked this two ways: the old code was kept in place and unit tests compare the two paths parameter by parameter, matching to 2e-5; and LSF job 102790 trained the same model twice for 200 optimizer steps with the same seed and data order, changing only which path was used.
  • A precision bug made uSSM-AR 2.6 times slower than it should have been. Diffusion.forward runs the backbone in FP32. The Transformer code switches back to bf16 inside itself, but the state space code did not. Only one configuration actually reaches that wrapper, because the block diffusion state space arms are routed elsewhere first, and that configuration is the autoregressive state space model. It therefore trained entirely in FP32 and never used the fast bf16 hardware. Fixing it cut training from 6h44m to 2h33m and cost only 0.00104 nats. Do not remove the FP32 wrapper. In bf16 the Transformer does not just lose a little accuracy, it fails to train at all.
  • The right-to-left scan is worth 44 percent of BiSSM's score. Turning it off at scoring time, with the same weights, drops MaveDB from +0.08519 to +0.04760 and costs 0.081 nats of NLL. This is the one architectural piece with a large and clean effect.
  • Block size makes no difference. At 128, 256 and 512 the NLL is 1.24637, 1.24749 and 1.24881, and |ρ| is 0.13090, 0.13404 and 0.13552. (These |ρ| values come from the block-size sweep, which scores at model length 512 and averages per seed, so the 256 entry reads 0.13404 rather than the 0.13330 two-seed ensemble in the first table.) The whole spread is 0.0046, which is smaller than the spread between two random seeds (0.007 to 0.008). The NLL ordering is just the NELBO bound getting tighter as blocks get smaller, not the model getting better.
  • Four more fixes cut memory by about 40 percent and made the autoregressive state space model the faster of the pair. We replaced a hand-written gated RMS norm with the fused kernel, padded the causal convolution instead of concatenating the previous state onto the input, shared the input and output projections between the forward and reverse scans, and folded the norm weight into the fused kernel on the Transformer side too. uSSM-AR went from 27.19 to 16.83 GiB and from 186,888 to 243,434 nucleotides per second; BiSSM-BD dropped 43 percent of its memory. Each change was checked in double precision and reproduces the original forward and backward values, so no trained model's likelihood moved. Before this work the state space model was 27 percent slower than the Transformer at the training length and used 1.69 times the memory, and we had written that this was intrinsic to Mamba-2. It was not; it was our code.
  • The state space models hold a far smaller generation cache. Measured while generating 2048 tokens, the state space cache is 5,038,080 bytes (4.80 MiB) and the Transformer cache is 56,623,104 bytes (54.0 MiB), a ratio of 11.2. Both stay constant during a run, but for different reasons, and that difference is the point. The state space cache is a fixed recurrent state whose size does not depend on context length at all. The Transformer cache is a key-value store pre-allocated for the full context, so it is constant only because it was sized for the maximum up front. Increase the context length and the Transformer cache grows with it, while the state space cache stays exactly the same.

Things to know before quoting these numbers

Added after the timescale and generation work.

Any τ figure quoted from the weights alone understates the real timescale by roughly 7–11×. Use the runtime measurement; the bias-only tool is valid only at initialisation, before the dt projection has learned to compensate.

The generation sweep has no quality axis. Low T is cheap and worse, and how much worse is unmeasured, so nothing here licenses a claim that block diffusion generates better per unit time — only faster.

Block-diffusion likelihoods are NELBO, an upper bound; autoregressive ones are exact. The gap between an AR and a BD column is a bound, not a measured difference.

On GenomicBenchmarks, prefer the median over seeds. The mean is not robust to the chance-level seeds that appear on the small tasks, and on dummy_mouse_enhancers a single dead seed moves an arm by more than most between-arm differences in the whole benchmark.

  • Use the signed ρ column, not |ρ|. The scorer takes the absolute value of each experiment's correlation before averaging (mavedb.py:278). That means an experiment the model gets backwards still adds to its score. All 12 experiments genuinely point the same way, so the sign should not be thrown away. The neg assays column counts how many of the 12 a model ranks backwards, and that is where the inflation comes from. Measured |ρ| divided by signed ρ is 1.13 for uSSM-AR and 1.17 for Transformer-AR, but 1.56 for Transformer-BD, 1.56 for BiSSM-BD and 1.54 for uSSM-BD. So the real gap between autoregressive and block diffusion is wider than the |ρ| column shows.
  • The runs do not all spend the same time on validation. Counted from the logs: uSSM-AR, Transformer-AR, BiSSM-BD and uSSM-BD each ran 320 validation passes, BiSSM C-a ran 160, and Transformer-BD ran only 80. So the gap is between Transformer-BD and everything else, not between the state space models and the Transformers. Use the train-only column when comparing architectures. With validation excluded, uSSM-BD costs 1.09 times Transformer-BD, not 1.19 times.
  • The block diffusion MaveDB scores are somewhat too low. We sampled 32 times per variant for the headline rows, and that is not fully converged: raising the count to 128 moves BiSSM from 0.13330 to 0.13689. Read the MC-32 rows as a slight underestimate. The autoregressive models compute an exact value, so they are not affected.
  • PLL is not a likelihood. It hides one position at a time and adds up the results, which is a useful stand-in but not the same quantity as an exact NLL, so do not compare it directly with dnaHNet's numbers. The one exception is a left-to-right backbone, where PLL is the exact autoregressive likelihood. Block diffusion has no exact likelihood at all; NELBO only puts an upper bound on it.
  • The partial ρ column comes from single runs. The signed ρ and |ρ| columns in the first table average two seeds. The partial ρ values are computed from one prediction file each. Compare partial against partial, not against the other columns.

Correction. An earlier version of this page said the trivial baseline scored 0.3649 and beat dnaHNet. That was wrong. It came from a pattern match ([A-Z][a-z]{2}\d+) that returns only three distinct values across all 21,250 variants, so it was reading a variant class code rather than counting substitutions. The correct figure is 0.30931. That still beats every model we trained, but it is below dnaHNet's 0.3266.

Three different ways of scoring appear on this page: exact autoregressive likelihood, diffusion NELBO, and pseudo-likelihood. They measure different things, so compare models scored the same way, and do not compare across the three. All likelihood values are in nats per nucleotide.
